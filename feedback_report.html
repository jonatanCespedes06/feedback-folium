Hallazgos

AltaSeguridad1. Escalada de privilegios en UserViewSet

folium_api/serializers.py:187-255 · folium_api/views.py:700-786

UserSerializer declara rol y password como campos escribibles, y UserViewSet solo exige IsLibrarianOrAdminUser. En consecuencia, una cuenta con rol LIBRARIAN puede:

  • PATCH /api/v1/user/{id}/ {"rol": "ADMIN"} sobre sí misma o sobre otro usuario: se autopromueve a administrador.
  • PATCH con password sobre la cuenta de un administrador y tomar control total de la misma.

Por qué importa. En un sistema con roles, la regla base es que nadie puede otorgarse más permisos de los que ya tiene. Un bibliotecario está pensado para tareas operativas; hoy puede convertirse en administrador o apropiarse de la cuenta del admin. En un despliegue real, eso equivale a entregar el control total del sistema a cualquier cuenta de personal.

Corrección sugerida. Restringir rol a administradores y limitar la edición de cuentas con privilegios:

# serializers.py · UserSerializer
def validate_rol(self, value):
    actor = self.context["request"].user
    if value == User.Rol.ADMIN and not (
        actor.is_superuser or actor.rol == User.Rol.ADMIN
    ):
        raise serializers.ValidationError(
            "Solo un administrador puede asignar el rol ADMIN."
        )
    return value

def update(self, instance, validated_data):
    actor = self.context["request"].user
    if "password" in validated_data and not (
        actor.is_superuser or actor.rol == User.Rol.ADMIN or actor.pk == instance.pk
    ):
        raise serializers.ValidationError(
            {"password": "No puedes cambiar la contraseña de otro usuario."}
        )
    return super().update(instance, validated_data)

Adicional: en UserViewSet.get_queryset(), excluir cuentas ADMIN/superusuario cuando el actor no sea administrador, para que ni siquiera puedan leerlas.

Riesgo de regresión Bajo. Solo bloquea operaciones que hoy deberían estar reservadas al administrador.

AltaPagos2. Suscripciones activables sin pago si MercadoPago no está configurado

folium_api/mercadopago_service.py:503-516 · folium_api/billing_views.py:276-311, 351-352

Cadena del problema:

  • Si falta MP_WEBHOOK_SECRET, el webhook omite la validación de firma y registra el evento como válido (billing_views.py:280, 290).
  • Si falta MERCADOPAGO_ACCESS_TOKEN, fetch_payment_details() devuelve {"status": "approved", "simulated": true} sin consultar a MercadoPago.
  • El webhook activa la suscripción cuando el estado es approved. Un tercero puede invocarlo con ?external_reference= conocido y activar un plan sin pagar.

Por qué importa. El webhook es el punto donde el backend decide si un pago ocurrió. Si acepta eventos sin verificar quién los envía, y además el modo simulado responde "aprobado" sin existir un pago real, cualquiera puede activar un plan sin pagar. En un producto de suscripciones eso es pérdida directa de ingresos y de confianza.

Corrección sugerida. No simular fuera de desarrollo y nunca activar con pagos simulados:

# mercadopago_service.py
def fetch_payment_details(self, payment_id: str) -> dict:
    if not self.is_configured:
        if settings.DEBUG:
            return {"id": payment_id, "status": "approved",
                    "status_detail": "simulated", "simulated": True}
        raise MercadoPagoServiceError("MercadoPago no está configurado en este entorno.")

# billing_views.py (antes de activate_period)
if payment_details.get("simulated"):
    return Response({"detail": "Pago simulado: no se activa la suscripción."},
                    status=status.HTTP_400_BAD_REQUEST)

Si el entorno expuesto ya tuvo DEBUG=True con este código, revisar suscripciones activas originadas en pagos con simulated=true.

MediaAutenticación3. Política de contraseñas configurada pero no aplicada

folium/settings.py:142-155 · folium_api/serializers.py:265-273, 318-327

AUTH_PASSWORD_VALIDATORS (longitud mínima real, contraseñas comunes, numéricas) existe, pero UserRegisterSerializer y UserSerializer solo imponen min_length=8. Registros como 12345678 o password son aceptados, contradiciendo la configuración. Es la vía natural de entrada de cuentas débiles.

Por qué importa. La política de contraseñas es una barrera que se define una vez y debe aplicarse en todos los lugares donde se crea o cambia una contraseña. Si está configurada pero no se usa, da una falsa sensación de seguridad y deja pasar cuentas fáciles de adivinar, que son el primer objetivo de un ataque de fuerza bruta.

# en ambos serializers
from django.contrib.auth.password_validation import validate_password
from django.core.exceptions import ValidationError as DjangoValidationError

def validate_password(self, value):
    try:
        validate_password(value)
    except DjangoValidationError as error:
        raise serializers.ValidationError(error.messages) from error
    return value

Riesgo de regresión Bajo. Puede exigir ajustar contraseñas usadas en demos o seeds.

MediaAutorización / datos4. /api/v1/items/ expone el inventario a cualquier usuario autenticado

folium_api/views.py:94 · README §7 "Ejemplares Físicos"

ItemViewSet usa IsLibrarianOrReadOnly, lo que permite GET a cualquier usuario con sesión (lectores incluidos): códigos de inventario y ubicaciones físicas quedan visibles. El README documenta ese endpoint como exclusivo de staff, por lo que código y documentación no coinciden.

Por qué importa. El inventario no es información pública: revela qué ejemplares existen, cuántos hay y dónde están físicamente. Un lector no necesita esos datos para usar el catálogo. Exponerlos amplía la superficie de ataque y contradice la regla que el propio equipo documentó, lo que además vuelve impredecible el modelo de permisos.

Corrección sugerida (si el portal lector no consume /items/):

class ItemViewSet(viewsets.ModelViewSet):
    permission_classes = [IsLibrarianOrAdminUser]  # antes: IsLibrarianOrReadOnly

Antes de aplicarlo, verificar en el frontend que el catálogo de lectores use /book/ y no /items/. Si /items/ se usa para mostrar disponibilidad pública, mantener el permiso y corregir el README.

MediaIntegridad5. La regla de estados de ejemplares no se aplica vía API

folium_api/models.py:145-162 · folium_api/serializers.py:399-421

Item.clean() impide pasar de LOST/DAMAGED a AVAILABLE directamente, pero DRF no invoca full_clean() al guardar: ItemSerializer no replica la regla. PATCH /api/v1/items/{id}/ {"status":"AVAILABLE"} sobre un ejemplar perdido o dañado se acepta, saltándose la FSM documentada en el README.

Por qué importa. Una máquina de estados solo sirve si todas las puertas de entrada la respetan. Si la API permite saltearla, un ejemplar marcado como perdido puede "reaparecer" como disponible y volver a prestarse. El inventario deja de ser confiable y los préstamos pasan a basarse en datos falsos.

# ItemSerializer
def validate_status(self, value):
    if (self.instance
            and self.instance.status in {Item.Status.LOST, Item.Status.DAMAGED}
            and value == Item.Status.AVAILABLE):
        raise serializers.ValidationError(
            "Un ejemplar perdido o dañado debe pasar por revisión antes de quedar disponible."
        )
    return value

Riesgo de regresión Bajo; los flujos normales (AVAILABLE→LOANED, LOANED→AVAILABLE) no se ven afectados.

MediaRobustez6. Filtros con valores no numéricos devuelven 500

folium_api/views.py:375-376 (year) · folium_api/views.py:113-114 (book en items)

qs.filter(publication_year=year) y qs.filter(book_id=book_param) reciben el valor crudo del query string. GET /api/v1/book/?year=abc o GET /api/v1/items/?book=abc producen ValueError y respuesta 500. Los demás filtros numéricos sí validan con isdigit(); estos dos quedaron sin guarda.

Por qué importa. Un 500 significa "el servidor falló", y acá en realidad el problema es un dato mal enviado por el cliente. Un error no controlado ensucia el monitoreo, tapa fallos reales y le devuelve al frontend una respuesta que no puede interpretar. El contrato esperable de una API es 400 para entradas inválidas.

# book
if year:
    if not str(year).isdigit():
        raise ValidationError({"year": "El año debe ser numérico."})
    qs = qs.filter(publication_year=int(year))

# items
if book_param:
    if not str(book_param).isdigit():
        raise ValidationError({"book": "El identificador de libro debe ser numérico."})
    qs = qs.filter(book_id=int(book_param))

MediaOperaciones7. Credenciales semilla conocidas

folium_api/management/commands/seed_data.py:411, 729 · README §9 paso 5

El comando crea admin / admin1234 (y credenciales equivalentes para bibliotecarios y lectores) e imprime las contraseñas. El auto-seed está protegido por DEBUG=True (apps.py:26), pero el comando manual no tiene esa guarda y el README lo incluye como paso opcional del despliegue en EC2. Si se ejecutó en el servidor, hoy existe una cuenta administradora con contraseña pública en el repositorio.

Por qué importa. Una contraseña que está escrita en el repositorio y en la salida del comando no es un secreto. Si esa cuenta existe en un servidor accesible, cualquier persona puede entrar como administrador con datos que ya conoce. Es una de las formas más comunes de comprometer un sistema en producción.

Acciones: si el entorno EC2 está accesible, rotar la contraseña de admin o desactivar la cuenta; quitar o marcar como solo-desarrollo el paso 5 del README; opcionalmente, en seed_data.handle(), abortar si DEBUG=False salvo --force.

BajaAutenticación8. Los errores 401 distinguen el motivo exacto del fallo

configuración por defecto de DRF (settings.py:185-189)

Con JWTAuthentication, las respuestas distinguen entre credenciales ausentes ("Authentication credentials were not provided"), token inválido ("Given token not valid...") y token expirado. Cada mensaje guía a quien esté probando el sistema sobre en qué paso falló.

Por qué importa. Los mensajes de error son información gratuita para un atacante: le permiten saber si la ruta existe, si el problema es el formato del token o su vigencia, y ajustar sus intentos. Un mensaje genérico para el cliente, con el detalle completo en los logs del servidor, elimina esa ventaja sin perder la capacidad de diagnosticar.

# folium_api/exceptions.py
from rest_framework.views import exception_handler
from rest_framework.exceptions import NotAuthenticated, AuthenticationFailed

def custom_exception_handler(exc, context):
    response = exception_handler(exc, context)
    if response is not None and isinstance(exc, (NotAuthenticated, AuthenticationFailed)):
        response.data = {"detail": "No autorizado."}
    return response

# settings.py · REST_FRAMEWORK
"EXCEPTION_HANDLER": "folium_api.exceptions.custom_exception_handler",

Riesgo de regresión Bajo. El detalle técnico se conserva en los logs.

BajaRobustez9. POST /api/v1/token sin barra final responde 500

folium/urls.py:27 · comportamiento de CommonMiddleware con APPEND_SLASH

La ruta existe solo como /api/v1/token/. Cuando llega un POST a /api/v1/token, Django intenta redirigir agregando la barra, pero no puede hacerlo conservando el cuerpo y el método, y lanza RuntimeError, que se traduce en 500. APPEND_SLASH ya está en su valor por defecto (True): este es el comportamiento documentado del framework, no una mala configuración.

Por qué importa. El código de estado le dice al cliente qué pasó, y un 500 indica un fallo del servidor. Acá el servidor está sano y el problema es la forma de la URL. Esos 500 ensucian los paneles de errores, esconden fallos reales y dejan al frontend sin una respuesta clara sobre qué corregir.

Opciones: (a) que el cliente use siempre la barra final, que es la convención de DRF y la solución más simple; (b) declarar también la ruta sin barra en urls.py; (c) APPEND_SLASH = False y definir explícitamente ambas formas. Documentar la convención en el README ayuda a que el equipo del frontend no vuelva a chocar con esto.

BajaEstabilidad10. Paginación sin orden explícito en el catálogo

folium_api/views.py:352-398 · salida de manage.py test

La suite emite UnorderedObjectListWarning: Pagination may yield inconsistent results with an unordered object_list: Book. BookViewSet.get_queryset() termina en distinct() sin order_by, por lo que un libro puede repetirse u omitirse entre páginas. El resto de los listados ya define un orden.

Por qué importa. La base de datos no garantiza el orden de las filas si no se pide uno explícito. Al paginar, esa falta de orden puede hacer que un mismo libro aparezca dos veces o que otro desaparezca al pasar de página. El usuario percibe un catálogo inconsistente y la suite ya lo está advirtiendo.

return qs.distinct().order_by("title", "id")

BajaRendimiento11. N+1 en serializers de libros

folium_api/serializers.py:639-651, 721-730, 799-808

get_total_items, get_available_items e get_is_available ejecutan obj.items.filter(...), que ignora el prefetch_related('items') del queryset e impacta la base por cada libro; get_is_available vuelve a calcular lo mismo. Con 20 libros por página son ~40–60 consultas adicionales. Con el catálogo actual (72 libros) no es un problema, pero es el primer cuello de botella al crecer.

Por qué importa. Cada consulta extra por fila multiplica el trabajo de la base de datos. Con pocos registros no se nota; es el patrón que hace que una API se vuelva lenta justo cuando el catálogo crece o cuando varios usuarios navegan a la vez. Detectar el N+1 temprano es más barato que optimizar después.

Opción de bajo riesgo: usar el prefetch en lugar de filtrar de nuevo:

def get_available_items(self, obj):
    items = obj.items.all()  # usa el cache del prefetch
    disponibles = sum(1 for i in items if i.status == Item.Status.AVAILABLE)
    pendientes = sum(
        1 for r in obj.reservations.all()
        if r.status == Reservation.StatusReservation.PENDING and r.item_id is None
    )
    return max(0, disponibles - pendientes)

Requiere incluir reservations en el prefetch_related de BookViewSet (ya está en list/retrieve).

BajaConfiguración12. MAILERS no existe como setting de Django

folium/settings.py:217-221

La configuración de email está escrita como MAILERS = {...}. Django lee EMAIL_BACKEND: el bloque actual no tiene efecto y cualquier envío de correo usará el backend por defecto (SMTP a localhost).

Por qué importa. Una configuración con un nombre inválido no falla de forma visible: simplemente se ignora. El resultado es que el correo nunca sale como se espera y el problema aparece recién cuando hay que notificar a un usuario, normalmente en el peor momento. Los settings que no existen no avisan.

EMAIL_BACKEND = "django.core.mail.backends.console.EmailBackend"
# en producción: smtp.EmailBackend + EMAIL_HOST / EMAIL_PORT / EMAIL_HOST_USER / EMAIL_HOST_PASSWORD

BajaDespliegue13. Endurecimiento de producción pendiente

folium/settings.py:185-189, 210-213

  • BasicAuthentication está habilitada globalmente: credenciales en base64 en cada request. En producción dejar solo JWTAuthentication y SessionAuthentication.
  • No hay SECURE_SSL_REDIRECT, SESSION_COOKIE_SECURE, CSRF_COOKIE_SECURE ni HSTS. Si el backend se sirve por HTTPS, conviene activarlos solo cuando DEBUG=False.
  • SECURE_BROWSER_XSS_FILTER fue eliminado en Django 4.0: es una línea muerta (no rompe nada).

Por qué importa. Las opciones de seguridad de Django están pensadas para activarse según el entorno. En desarrollo conviene la comodidad; en producción, HTTPS obligatorio y cookies protegidas son la diferencia entre una sesión que viaja cifrada y una que puede copiarse en una red pública. BasicAuth, además, expone la contraseña en cada request.

if not DEBUG:
    REST_FRAMEWORK["DEFAULT_AUTHENTICATION_CLASSES"] = [
        "rest_framework_simplejwt.authentication.JWTAuthentication",
        "rest_framework.authentication.SessionAuthentication",
    ]
    SECURE_SSL_REDIRECT = True
    SESSION_COOKIE_SECURE = True
    CSRF_COOKIE_SECURE = True
    SECURE_HSTS_SECONDS = 31536000

Verificar que el proxy/balanceador reenvíe X-Forwarded-Proto y configurar SECURE_PROXY_SSL_HEADER antes de activar la redirección, para evitar bucles.

BajaConcurrencia15. Préstamos sin bloqueo de fila

folium_api/serializers.py:856-899 · contraste con folium_api/views.py:947-966

La creación de reservas usa transaction.atomic() + select_for_update(), pero la de préstamos valida disponibilidad y escribe sin bloqueo. Dos POST /api/v1/loan/ simultáneos sobre el mismo ejemplar pueden pasar la validación y crear dos préstamos activos. No hay restricción de base que lo impida.

Por qué importa. Dos clics rápidos, dos pestañas o un reintento del frontend pueden llegar casi al mismo tiempo. Sin bloqueo, ambas peticiones ven el mismo ejemplar como disponible y lo prestan dos veces; el sistema queda con un préstamo imposible de cumplir y el inventario descuadrado. El problema es raro, pero aparece justo cuando hay más actividad.

Opción mínima (patrón ya usado en reservas):

def create(self, validated_data):
    with transaction.atomic():
        item = Item.objects.select_for_update().get(pk=validated_data["item"].pk)
        validated_data["item"] = item
        # (revalidar item.status == AVAILABLE aquí)
        loan = super().create(validated_data)
        item.status = Item.Status.LOANED
        item.save(update_fields=["status", "updated_at"])
        # ...

En desarrollo con SQLite el bloqueo no aplica; el riesgo real aparece con PostgreSQL en producción. Puede quedar como mejora posterior a la entrega.

BajaHardening16. Importador sin límites de tamaño

folium_api/importer_views.py:1185-1200, 450-511

Los endpoints del importador no verifican uploaded_file.size, y parse_xlsx_file descomprime y parsea el XML completo en memoria sin tope: un archivo comprimido pequeño puede inflarse y agotar memoria. El endpoint exige rol bibliotecario/admin (superficie acotada), por lo que es defensa en profundidad, no un hueco abierto.

Por qué importa. Aceptar archivos sin límite permite que un solo request consuma toda la memoria del servidor y lo tumbe. Aunque hoy solo lo use personal de confianza, poner un tope es una defensa barata que también protege contra errores humanos, como subir el archivo equivocado.

MAX_IMPORT_BYTES = 10 * 1024 * 1024
if uploaded_file.size > MAX_IMPORT_BYTES:
    return Response({"detail": "El archivo supera el límite de 10 MB."},
                    status=status.HTTP_400_BAD_REQUEST)

InformativaCalidad17. Menores

  • Favoritos duplicados: FavoriteSerializer.create usa get_or_create (serializers.py:1099-1101); un duplicado responde 201 como si se hubiera creado. Por qué importa: un 201 sobre algo que ya existía confunde al frontend y hace difícil distinguir éxito de duplicado.
  • Import implícito: views.py:767 usa re.sub pero re llega por from .serializers import *. Por qué importa: funciona por casualidad; un refactor de imports lo rompe en runtime sin ningún aviso previo.
  • Warnings W042 (13): Django sugiere declarar el tipo de PK. Se silencian sin migraciones con DEFAULT_AUTO_FIELD = "django.db.models.AutoField" (coincide con el esquema actual). Por qué importa: no rompen nada, pero un equipo que se acostumbra a ignorar warnings puede pasar por alto uno que sí importe.
  • Idioma: LANGUAGE_CODE = "en-us" con mensajes propios en español; Por qué importa: los errores automáticos de Django (validadores, unicidad) saldrán en inglés, generando una experiencia mixta y más consultas de soporte.
  • BookViewSet.options: el nombre de la acción (views.py:462) pisa el manejador HTTP OPTIONS de DRF en ese ViewSet. Por qué importa: usar un nombre que el framework reserva puede cambiar el comportamiento de metadata de forma difícil de rastrear; conviene renombrarla (p. ej. book_options con url_path="options").

Verificado como correcto

  • JWT: rotación de refresh tokens con blacklist activa; access de 15 minutos.
  • Permiso por defecto IsAuthenticated; permisos explícitos y consistentes en la mayoría de los ViewSets; propietario forzado en favoritos, reservas y reseñas.
  • Throttling global y específico para login (30/min).
  • Entrega de /media/ con validación de path traversal, ETag/304 y cabeceras de caché.
  • Webhook de MercadoPago: HMAC con comparación en tiempo constante y ventana anti-replay de 300 s; montos tomados del catálogo del servidor, nunca del cliente.
  • Soft delete coherente (libros, usuarios, reseñas) y reutilización de ISBN de libros dados de baja.
  • Whitelists de ordenamiento en /loan/ y /reservations/ (sin inyección por ordering).
  • Suite de pruebas: 70 tests en verde.
