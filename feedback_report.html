src/components/Login&RegisterComponents/AuthSidebar.jsx:4-7, 48-74 · src/components/Layouts/AuthLayout.jsx:22-25

F3. Cancelación de reservas con tres contratos distintos, incluido DELETE destructivo

src/components/CatalogSearchComponents/CatalogBookCard.jsx:122-133 · src/pages/UserReservations.jsx:101-137 · src/pages/ReservationDashboard.jsx:239-288 · src/api/services/reservationService.js:5-12

La misma acción se ejecuta de tres maneras:

  • En el catálogo, CatalogBookCard llama a reservationService.remove(reservationId), que hace DELETE /reservations/{id}/ y borra el registro.
  • En “Mis reservas”, UserReservations hace PATCH con status: "CANCELLED".
  • En el panel de bibliotecario, ReservationDashboard también hace PATCH de estado.

El backend expone una acción específica POST /reservations/{id}/cancel/, pero reservationService.js no la utiliza. En el catálogo, además, el error de cancelación solo se registra en consola (CatalogBookCard.jsx:128-130) y el usuario no recibe feedback.

Por qué importa. Una reserva es un registro operativo: sirve para auditoría y para entender qué pasó con un ejemplar. Si el catálogo la elimina físicamente, se pierde ese historial. Usar tres caminos distintos también implica que una futura regla de negocio (por ejemplo, penalizaciones o notificaciones) se aplique en un lugar y no en los otros. La acción canónica comunica mejor la intención y concentra las validaciones.

Corrección sugerida. Agregar el método al servicio y reemplazar las tres llamadas:

export const reservationService = {
  getAll:  (params)   => api.get(BASE, { params }),
  getSummary: ()     => api.get(`${BASE}summary/`),
  getById: (id)       => api.get(`${BASE}${id}/`),
  create:  (data)     => api.post(BASE, data),
  update:  (id, data) => api.put(`${BASE}${id}/`, data),
  patch:   (id, data) => api.patch(`${BASE}${id}/`, data),
  cancel:  (id)       => api.post(`${BASE}${id}/cancel/`),
};

Luego usar reservationService.cancel(id) en el catálogo, en “Mis reservas” y en el panel de reservas. Conviene eliminar remove si no queda otro uso.

Riesgo de regresión Bajo. La acción ya existe; hay que probar la cancelación desde las tres pantallas y mostrar el error cuando falle.

F6. El parámetro year sin validar provoca un 500 del backend

src/hooks/useBooks.js:12-20, 91-96 · src/components/BookCatalogComponents/CatalogSearch.jsx:112-116 · src/components/CatalogSearchComponents/FilterSidebar.jsx:84-92

El filtro de año se lee directamente de la URL con searchParams.get("year") y se envía tal cual a la API. No hay validación intermedia. Un enlace como /catalog?year=abc hace que el backend intente convertir el valor a entero y falle con un 500. El input type="number" no protege contra una URL editada, un marcador viejo o un valor programático.

Por qué importa. Un 500 indica “falló el servidor”, aunque el problema real sea un parámetro inválido. El catálogo se rompe para quien abre ese enlace, y el error queda registrado como si fuera una falla de infraestructura. La respuesta correcta para una entrada inválida es ignorarla o rechazarla antes de llamar a la API.

Corrección sugerida. Validar en el hook y mantener el número en el envío:

const validYear = (value) =>
  /^\d{4}$/.test(String(value)) ? String(value) : "";

year: validYear(searchParams.get("year")) || defaults.year,

if (currentFilters.year) params.year = Number(currentFilters.year);

También conviene agregar min="868" y max={new Date().getFullYear()} en el input, y un guard equivalente en el backend como defensa en profundidad.

Riesgo de regresión Bajo. Los años válidos siguen funcionando igual.

F7. Portadas sin fallback cuando la imagen falla

src/components/BookCatalogComponents/BookCard.jsx:196 · src/components/BookDetailComponents/BookCover.jsx:85 · src/components/CatalogSearchComponents/CatalogBookCard.jsx:165 · src/pages/UserReservations.jsx:299 · src/pages/UserLoans.jsx:235 · src/components/InventoryComponents/InventoryTable.jsx:289, 413 · src/pages/LoanCounter.jsx:678, 840

Las portadas se muestran con <img> y no tienen onError. El fallback tipográfico solo aparece cuando cover es null, no cuando la URL existe pero la imagen devuelve 404 o falla la red. sanitizeMediaUrl normaliza la ruta, pero no puede evitar una respuesta fallida.

Por qué importa. El catálogo es visual: una portada rota en una tarjeta se ve como un recuadro vacío o el ícono de imagen rota del navegador. Es una falla frecuente cuando se migran archivos, se borra una portada o hay un problema temporal de almacenamiento. Un fallback mantiene la ficha legible y evita que el usuario piense que el libro no existe.

Corrección sugerida. Centralizar la imagen en un componente compartido:

const [failed, setFailed] = useState(false);

return failed ? (
  <CoverFallback title={title} />
) : (
  <img src={cover} alt={title} onError={() => setFailed(true)} />
);
Riesgo de regresión Bajo. Solo cambia la presentación cuando la imagen no carga.

F10. Catálogo de planes duplicado y éxito de pago declarado antes de verificar

src/api/services/billingService.js:7-189, 193-222 · src/pages/LibraryPricingPage.jsx:58, 84-98, 118-154, 162-176

El frontend mantiene una copia completa de los planes y precios en DEFAULT_LIBRARY_PLANS. Si /billing/plans/ falla o devuelve códigos antiguos, la página sigue mostrando ese catálogo local. Por otro lado, al volver de MercadoPago se muestra el banner de “Suscripción activada” basándose en payment_status=approved de la URL; la verificación server-to-server se intenta después y cualquier error se ignora.

Por qué importa. Los importes y límites deben venir de una sola fuente. Si cambian los precios en el servidor y el fallback queda viejo, la interfaz muestra un número distinto del que se cobra. Además, declarar “activada” antes de que el backend confirme el pago puede dejar al usuario con una expectativa falsa si el webhook todavía no procesó la transacción.

Corrección sugerida. Mostrar el catálogo del servidor como fuente principal (con estado de carga y error visibles), y confirmar el pago antes de anunciar la activación:

getPlans: async () => {
  const response = await api.get(`${BASE}plans/`);
  return response.data;
}

const result = await billingService.verifyPaymentStatus({
  payment_id: paymentId,
  external_reference: extRef,
});
if (result?.approved) setPaymentBanner(successBanner);

Si el fallback se conserva, etiquetarlo como “precios de referencia” y no usarlo para iniciar un checkout. En modo simulación, el mensaje debe decir claramente que no hubo un pago real.

F13. Validación de formularios fácilmente evadible y manejo de errores insuficiente

src/components/ProfileComponents/UserProfile.jsx:95-120 · Lógica de guardado del perfil

El formulario de edición de perfil confía exclusivamente en atributos HTML (required, type="email") para la validación. Durante las pruebas, se comprobó que eliminando el nodo del input desde las herramientas de desarrollador se puede realizar un envío con campos vacíos o inválidos, saltándose la protección del cliente.

Además, ante respuestas de error del servidor (HTTP 400), el feedback visual es insuficiente: el usuario reporta que la pantalla puede quedar sin renderizar contenido relevante o sin mostrar un mensaje de error claro (como un snackbar o alerta), lo que genera una mala experiencia de usuario.

Por qué importa. La validación en el cliente es solo una ayuda de usabilidad, no una medida de seguridad. Un sistema robusto debe validar los datos programáticamente en el handleSubmit antes de llamar a la API para evitar envíos basura. Por otro lado, la gestión de errores debe ser "ruidosa": si algo falla, el usuario debe saber exactamente qué pasó y cómo solucionarlo mediante indicadores visuales consistentes.

Corrección sugerida. Implementar una validación manual previa al envío y usar un sistema de notificaciones global:

const handleSave = async (e) => {
  e.preventDefault();
  // 1. Validación programática
  if (!formData.first_name?.trim() || !formData.email?.includes('@')) {
    return setEditError("Por favor, completa los campos obligatorios correctamente.");
  }
  
  try {
    // ... llamada a la API
  } catch (err) {
    // 2. Manejo de error con feedback claro
    showToast("Error al actualizar el perfil", "error");
    setEditError(err.response?.data?.detail || "Datos inválidos");
  }
};

1. Escalada de privilegios en UserViewSet

folium_api/serializers.py:187-255 · folium_api/views.py:700-786

UserSerializer declara rol y password como campos escribibles, y UserViewSet solo exige IsLibrarianOrAdminUser. En consecuencia, una cuenta con rol LIBRARIAN puede:

  • PATCH /api/v1/user/{id}/ {"rol": "ADMIN"} sobre sí misma o sobre otro usuario: se autopromueve a administrador.
  • PATCH con password sobre la cuenta de un administrador y tomar control total de la misma.

Por qué importa. En un sistema con roles, la regla base es que nadie puede otorgarse más permisos de los que ya tiene. Un bibliotecario está pensado para tareas operativas; hoy puede convertirse en administrador o apropiarse de la cuenta del admin. En un despliegue real, eso equivale a entregar el control total del sistema a cualquier cuenta de personal.

Corrección sugerida. Restringir rol a administradores y limitar la edición de cuentas con privilegios:

# serializers.py · UserSerializer
def validate_rol(self, value):
    actor = self.context["request"].user
    if value == User.Rol.ADMIN and not (
        actor.is_superuser or actor.rol == User.Rol.ADMIN
    ):
        raise serializers.ValidationError(
            "Solo un administrador puede asignar el rol ADMIN."
        )
    return value

def update(self, instance, validated_data):
    actor = self.context["request"].user
    if "password" in validated_data and not (
        actor.is_superuser or actor.rol == User.Rol.ADMIN or actor.pk == instance.pk
    ):
        raise serializers.ValidationError(
            {"password": "No puedes cambiar la contraseña de otro usuario."}
        )

9. POST /api/v1/token sin barra final responde 500

folium/urls.py:27 · comportamiento de CommonMiddleware con APPEND_SLASH

La ruta existe solo como /api/v1/token/. Cuando llega un POST a /api/v1/token, Django intenta redirigir agregando la barra, pero no puede hacerlo conservando el cuerpo y el método, y lanza RuntimeError, que se traduce en 500. APPEND_SLASH ya está en su valor por defecto (True): este es el comportamiento documentado del framework, no una mala configuración.

Por qué importa. El código de estado le dice al cliente qué pasó, y un 500 indica un fallo del servidor. Acá el servidor está sano y el problema es la forma de la URL. Esos 500 ensucian los paneles de errores, esconden fallos reales y dejan al frontend sin una respuesta clara sobre qué corregir.

Opciones: (a) que el cliente use siempre la barra final, que es la convención de DRF y la solución más simple; (b) declarar también la ruta sin barra en urls.py; (c) APPEND_SLASH = False y definir explícitamente ambas formas. Documentar la convención en el README ayuda a que el equipo del frontend no vuelva a chocar con esto.

11. N+1 en serializers de libros

Por qué importa. Cada consulta extra por fila multiplica el trabajo de la base de datos. Detectar el N+1 temprano es más barato que optimizar después.

Opción de bajo riesgo: usar el prefetch en lugar de filtrar de nuevo:

def get_available_items(self, obj):
    items = obj.items.all()  # usa el cache del prefetch
    disponibles = sum(1 for i in items if i.status == Item.Status.AVAILABLE)
    pendientes = sum(
        1 for r in obj.reservations.all()
        if r.status == Reservation.StatusReservation.PENDING and r.item_id is None
    )
    return max(0, disponibles - pendientes)

Requiere incluir reservations en el prefetch_related de BookViewSet (ya está en list/retrieve).
